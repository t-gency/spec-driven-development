# Design Rationale — Staged Engineering Methodology

> **Purpose:** explain to a teammate (or future contributor) *why* this
> methodology and the templates and skill that support it look the way they
> do. This is the design memo for the methodology itself, not for any
> particular feature built with it.
>
> **Audience:** an engineer or PM who has been handed this folder and wants
> to understand the choices encoded in it.
>
> **Date:** 2026-05-05 · **Status:** Initial version.

---

## 1. The methodology at a glance

Three documents per feature, each consumed and produced sequentially:

```
   Concept Note            Spec                   Implementation Plan
─────────────────────  ─────────────────────  ─────────────────────────
why + direction         what + behaviour        what + where + order
problem, vision,        FRs, NFRs, scenarios,   modules, paths,
alternatives,           acceptance criteria     branches, tests,
decisions, PoCs                                 rollout
─────────────────────  ─────────────────────  ─────────────────────────
   ↑          ↓             ↑          ↓             ↑
   └──────────┴─────────────┴──────────┴─────────────┘
        each doc stands alone; either neighbour can be derived from it
```

Two properties matter:

1. **Each document stands on its own.** A reader who only has the Spec
   should be able to understand the feature; same for the Plan or the
   Concept Note.
2. **Bidirectional derivability.** From any one document, a competent
   reader (human or AI) should be able to reconstruct the previous or
   next stage. This is what makes the workflow usable by AI coding
   agents — the docs are deliberately designed as machine-readable
   handoff contracts, not just human prose.

## 2. Design principles

These are the principles every template, every guidance file, and every
question set is shaped around:

- **Templates are normative.** Section IDs and headings are the
  agent-readable backbone. We do not invent new sections per feature; we
  fill the existing ones, or explicitly mark them not applicable.
- **Cite, don't paraphrase.** Cross-references between docs use stable
  IDs (`D-01`, `FR-005`, `AC-10`, `TD-02`, `OPEN-Q-03`). When the Spec
  inherits a Concept-Note decision, it cites `D-01` rather than
  re-stating the decision in prose.
- **Surface unknowns.** `[OPEN-Q-N]` and `[INFERRED]` markers are
  first-class outputs. A doc with honest unknowns beats a doc with
  confident fabrication.
- **Quantify everything quantifiable.** "Fast", "secure", "robust" are
  guesses; `p95 < 200 ms`, `OWASP ASVS L2`, `99.9% monthly` are
  contracts.
- **Behaviour-first specs.** Functional requirements use **EARS**
  syntax; scenarios use **Given/When/Then**. Both formats produce
  single-clause, testable obligations LLMs implement faithfully.
- **Phased delivery.** Implementation Plans split work into branches
  behind a feature flag, each independently mergeable, testable, and
  revertible.
- **Progressive disclosure for the skill.** `SKILL.md` is short and
  always loaded; templates, guidance, and question sets only enter
  context when the skill actually starts authoring a doc of that type.
  The three supporting-file roles are deliberately distinct: a
  **template** is the artefact's structure (what to produce), a
  **reference / guidance file** is craft knowledge (how to produce it
  well), a **question set** is the interview script (how to elicit the
  content from the user). Each is loaded at a different time. See
  MD-13 in §5 for why they're not collapsed.

## 3. Research summary

The methodology was informed by four parallel research investigations,
covering Concept Notes, Specs, Implementation Plans, and Claude Code
Skill mechanics. Highlights:

### 3.1 Concept Note — what industry does

| Source | What we adopted |
|---|---|
| Google "Design Docs at Google" (Malte Ubl) | The *Goals / Non-goals / Context / Alternatives Considered* quartet — the most-copied structure in the industry. |
| Amazon PRFAQ / "Working Backwards" | The press-release framing for §5 Vision; forces clarity on user-visible value before architecture. |
| Basecamp Shape Up | The *appetite* concept (time budget) and explicit "rabbit holes" / "no-gos". |
| GitLab handbook / Rust RFCs / Python PEPs | Explicit "Drawbacks", "Unresolved Questions", "Future Possibilities" patterns. |
| GitHub Spec Kit (`/specify → /plan → /tasks`) | Stable section headings + atomic decision IDs that downstream stages can cite. |
| AWS Kiro spec methodology | "Settled / Decide later / Must remain non-goals" handoff section to the next stage. |
| Anthropic context / prompt engineering guidance | Front-load machine-parseable structure; tag open questions inline; link rather than inline large artefacts. |
| ThoughtWorks Lean Inception | Hypothesis framing for the §7 Research section. |

### 3.2 Spec — formats that work for both humans and LLMs

| Source | What we adopted |
|---|---|
| EARS (Mavin et al.) | Five canonical patterns (Ubiquitous, Event-driven, State-driven, Optional feature, Unwanted behaviour) for §7 functional requirements. Industrial studies (arXiv 2504.07244) show ~50 % reduction in LLM coding errors when EARS-style FRs are used. |
| Cucumber / BDD lineage | Given/When/Then for §9 scenarios; we use the structure without committing to BDD tooling. |
| ISO/IEC/IEEE 29148:2018 | Modern successor to IEEE 830; stable IDs per requirement. |
| Google design docs | Goals/Non-goals pairing carried into §3 of the Spec. |
| Linear / Shape Up | Co-located acceptance criteria per requirement; reduces lookup distance. |
| Stripe / GitLab handbook | First-class "Open Questions" block; reviewers must engage with them. |
| AWS Kiro `requirements.md` | EARS-formatted requirements as the default. |
| GitHub Spec Kit | Stable IDs (`FR-001` etc.) so LLMs can cite them back without re-quoting. |
| Anthropic prompt engineering | Single requirement per line, glossary defined once, NFRs always quantified, inline `[OPEN-Q]` / `[ASSUMPTION]` markers. |

### 3.3 Implementation Plan — what makes it agent-executable

| Source | What we adopted |
|---|---|
| Google design docs | Status field + reviewer table; Context → Goals/Non-goals → Design → Alternatives → cross-cutting (security, privacy, observability). |
| Stripe writing culture (Increment) | Short, decision-dense docs; explicit ownership and reviewer sign-off. |
| GitLab handbook (engineering principles + DB migrations) | Iteration / minimum-viable-change phasing; expand-migrate-contract for DB changes. |
| Shopify engineering | Feature flags by default; small reversible deploys. |
| GitHub Spec Kit | Flat checkbox `tasks.md`; `[P]` parallelism markers; dependency tags. |
| AWS Kiro `tasks.md` | Tasks reference design symbols by name; agent advances one checkbox at a time. |
| Anthropic Claude Code (plan mode + subagents) | Plans that name files and exported symbols are executed more faithfully than narrative ones. |
| Cursor rules + plans | Plan = *what + where + order*; rules = *how*. Don't conflate them. |
| OpenAI Copilot Workspace | Plan → Implement → Verify loop; the plan lists each file with a one-line intent before edits begin. |
| Hodgson on feature flags (martinfowler.com) | Canonical flag taxonomy: release toggles, ops toggles, kill switches. |

Agent-priority list (ordered by what an agent actually needs):

1. Exact file paths.
2. Exact symbol names.
3. Function signatures, not bodies.
4. Edit shape per file (`create`, `add function X`, `modify Y to also do Z`, `delete`).
5. Per-task acceptance check (a test passes, a command exits 0).
6. Dependency arrows (`[P]` markers).
7. Spec anchors on every non-trivial choice.

What we **avoid** putting in plans:

- Full code blocks (bloats context, traps agents into stale impls).
- Open-ended "considerations".
- Re-derivations of Spec content.

### 3.4 Claude Code Skill mechanics

| Finding | What we adopted |
|---|---|
| Single skill > multiple for tightly coupled artefacts | One `staged-engineering-doc` skill, not three. |
| Marketplace-based distribution for team-shared methodologies | The skill ships inside a plugin (`engineering-methodology`) hosted in a marketplace declared by the repository that carries it (`tgency-method`); users install the whole plugin in one command (e.g. `/plugin install engineering-methodology@tgency-method` for Claude Code). |
| Description field is the trigger | Verbs (produce, derive, turn into, generate) + all doc-type names. |
| Progressive disclosure | `SKILL.md` orchestrates; templates, guidance, and question sets are loaded on demand. |
| Q&A > one-shot generation | Question-set checklists drive interview-style authoring. |

References: official Claude Code skill docs at code.claude.com/docs/en/skills,
the `anthropics/skills` repository, and community examples from the
Composio "awesome-claude-skills" list.

## 4. How your example docs became templates

We read all three of your existing example docs (`DOCUMENT_UPLOAD_*` in
`t-gency-hubs-requirements-agent`) end-to-end and refactored their
patterns into reusable shapes. Three buckets:

### 4.1 Patterns kept verbatim from your examples

| Your pattern | Where it lives in the templates |
|---|---|
| Status / Date / cross-link header at the top of every doc | Header block in all three templates |
| Numbered sections with stable headings | Preserved across all three templates |
| Strategy-comparison table with multi-dimension scoring (your concept's §8) | Concept §9.3 "Comparison summary (optional)" |
| `Spec ref: §X` annotations under every plan subsection | Implementation Plan §7.x.2–§7.x.5 |
| Per-branch tracker table (status / PR / tests / notes) | Implementation Plan §7.1 |
| Branch dependency ASCII diagram | Implementation Plan §7.1 |
| AGENTS.md compliance reference | Implementation Plan §5 |
| Per-branch Definition of Done checklist | Implementation Plan §6 |
| Per-branch sub-structure (decisions / types / constants / config / interfaces / tests / verification / files inventory) | Implementation Plan §7.2.1–§7.2.8 |
| "Files inventory: New / Modified / Deleted" blocks | Implementation Plan §7.x.8 + §16 master roll-up |

### 4.2 What we added (from research, not in your examples)

| Addition | Source | Why |
|---|---|---|
| TL;DR section in the Concept Note | Google design docs, Amazon PRFAQ | Front-loaded summary; humans and LLMs read it first |
| Atomic decision IDs (`D-01`, `D-02`, …) with reversibility column | Bezos one-way/two-way doors; ADR conventions | Spec/Plan can cite without re-quoting prose |
| `[OPEN-Q-N]` and `[INFERRED]` markers as first-class | Anthropic context engineering, AWS Kiro | Forces honesty about unknowns |
| EARS preamble + five-pattern table for FRs | Mavin et al.; industrial LLM studies | Single-clause requirements LLMs implement faithfully |
| Given/When/Then scenarios in §9 of the Spec | BDD lineage | Executable contract; doubles as test scaffolding |
| Quantified NFR table with category column | IEEE 29148; Stripe writing culture | Replaces "fast" / "secure" with measurable contracts |
| Dedicated §4 Technical & architectural constraints (TC-*) in the Spec | Your example doc's §3 "Platform and integration constraints"; ARC42 cross-cutting concerns | Solution-space mandates have a home distinct from FRs and NFRs |
| Handoff sections in Concept (§16) and Spec (§17) | GitLab "Future Possibilities"; Kiro | Explicit contract with the next-stage author/agent |
| Acceptance Criteria coverage matrix in the Plan (§17) | Kiro `tasks.md`; spec-driven dev | Mechanical Plan ↔ Spec consistency check |
| `[P]` parallelism markers on per-branch task checklists | GitHub Spec Kit | Lets agents fan tasks to subagents |
| Expand-migrate-contract migration sequence | GitLab handbook | Default safe pattern for DB changes |
| Risks & rollback table with detection signal + exact procedure | Stripe Increment; Hodgson on flags | Forces operability thinking at plan time |
| Bidirectional derivation guidance in `SKILL.md` | Your "any doc creates the previous or next" requirement + spec-driven dev research | Makes the workflow a true 3-way pipeline |
| Glossary section in the Spec | IEEE 29148; LLM hallucination research | Pin domain vocabulary once to prevent drift |

### 4.3 What we changed (your example was project-specific; templates are generic)

| Your example was… | The template is… |
|---|---|
| Inline strategy-comparison tables (Strategies A–E) | Generalised to "Alternatives considered" with per-alternative subsections + optional comparison table |
| GEAI / coda-core constraints inline in the spec | Replaced by Glossary, Constraints inherited from Concept (§3.3), Technical & architectural constraints (§4 TC-*), Dependencies (§13) |
| Free-form prose for FRs ("The system shall …") | EARS five-pattern FRs with stable IDs |
| Acceptance criteria in a single bullet list | Split into Functional / Non-functional / Constraint compliance / Negative (§11.1 / §11.2 / §11.3 / §11.4), each with FR/NFR/TC cross-references |
| Branch numbers 1–6 hard-coded | Generalised to a 5-branch arc (scaffolding → core write → core read → edge cases → rollout) |
| Implementation-status callouts ("Implemented:", "Deferred:") | Removed from the template body — these belong in real docs, not templates |
| Industry context specific to ChatGPT / NotebookLM / Gemini | Generalised to §7 "Research & industry context" with subsections for peer products, prior art, and PoCs |

### 4.4 What we deliberately left out

- **Full code blocks in the Plan.** The template prescribes signatures
  and acceptance checks but stops short of code, per agent-execution
  research that says inline code blocks bloat context and trap agents
  into stale implementations.
- **Vendor-specific sections.** Anything GEAI-, coda-core-, or
  omni-parser–specific is an accident of the example feature; the
  template stays platform-neutral.

## 5. Key decisions encoded in the methodology

These are the decisions a teammate is most likely to question. Each
should be defensible without re-reading this document.


| ID | Decision | Rationale | Reversibility |
|---|---|---|---|
| MD-01 | Three documents (Concept Note, Spec, Implementation Plan) | Mirrors the dominant industry pattern (Google one-pager + design doc; GitHub Spec Kit's specify/plan/tasks; Kiro's requirements/design/tasks). Two stages collapse the *why* and *what*; four stages add ceremony without value. | Hard |
| MD-02 | Bidirectional derivability between adjacent docs | Lets AI agents and humans pick up at any stage; reduces the "must always start at Concept" tax. | Hard |
| MD-03 | EARS for functional requirements | Empirically reduces LLM implementation errors; constrains authors into single-clause FRs. | Easy (templates can switch to free-form FRs) |
| MD-04 | Given/When/Then for scenarios | Shared mental model with QA; LLMs translate to tests reliably. | Easy |
| MD-05 | Stable IDs (`D-`, `FR-`, `NFR-`, `TC-`, `AC-`, `TD-`, `S-` with optional `[a-z]*` variant suffix from MD-22, `US-`, `A-`, `R-`, `IMP-`, `OBS-`, `T-N.{C,D,N}*` for tasks, `OPEN-Q-`) | Cross-references survive doc edits; LLMs cite IDs instead of paraphrasing. One ID prefix per template section. Scenario IDs are `S-NN` for parent scenarios and `S-NNa` / `S-NNb` / … for letter-suffixed variants (MD-22) — the regex `S-[0-9]+[a-z]*` matches both. Task IDs (`T-`) are compound — `T-<branch>.<kind><N>` where `<kind>` is `C` for commit, `D` for DoD, or a plain integer for implementation tasks (e.g. `T-1.1`, `T-2.C3`, `T-3.D8`, `T-3.D8b` for sub-DoD tasks). | Hard (changing ID schemes is disruptive) |
| MD-06 | Branch-with-flag phasing in the Plan | Each branch independently mergeable / revertible; matches the dominant "small reversible deploys" pattern at GitLab/Shopify/Stripe. | Easy (teams can use a single-PR style if they want) |
| MD-07 | Single skill (`staged-engineering-doc`) over per-doc skills | Three docs are a tight pipeline; one orchestrator handles forward and backward derivation cleanly. Avoids skill bloat. | Easy |
| MD-08 | Question sets as separate files (not inline in `SKILL.md`) | Progressive disclosure keeps `SKILL.md` short; teams can edit the interview without touching the orchestrator. | Easy |
| MD-09 | Templates are platform-neutral | Lets the methodology be reused across products and stacks; project-specific conventions go into `AGENTS.md` referenced from the Plan's §5. | Easy |
| MD-10 | `[OPEN-Q-N]` and `[INFERRED]` are first-class output | Honesty currency; the alternative is silent fabrication. | Easy |
| MD-11 | The Spec carries three flavours of normative content — FRs (§7), NFRs (§8), and Technical / architectural constraints (§4 TC-*) — in separate sections, not mixed. | FRs answer "what shall the system do?"; NFRs answer "what quality shall it achieve?"; TCs answer "which solutions are admissible?". Mixing them confuses authors and downstream agents. The example doc had this implicitly (its §3 "Platform and integration constraints"); we made it explicit. Engineering-judgement design pattern choices (Strategy, Repository, …) explicitly stay in the Plan as `TD-*`. | Easy |
| MD-12 | Default `Base branch` for every branch in the Plan is the team's trunk (`main` / `develop`), not the previous feature branch. | The whole point of feature-flag-gated branches is that each can be merged independently and the next can be cut from trunk. Stacking branches (Branch N based on Branch N-1) bakes in cascading rebases and discourages independent mergeability. The arrow diagram in §7.1 represents *intended merge order*, not git topology. The example doc that inspired this template stacked its branches; we deliberately departed from that. Stacking remains permitted as an escalation when a branch genuinely cannot compile/test without uncommitted code from a predecessor — but it must be flagged in the tracker's Notes column with the reason. | Easy |
| MD-13 | The skill keeps three kinds of supporting file separate — `templates/` (artefact structure), `references/` (authoring craft / guidance), `question-sets/` (interview script). | Three orthogonal concerns, hence three files: a **template** tells you *what to produce*; a **reference** tells you *how to produce it well*; a **question set** tells you *how to elicit the content*. Each is loaded at a different time, which keeps the agent's working context tight (progressive disclosure). Folding any pair together has costs: putting guidance inline in templates as HTML comments bloats the artefact and risks the meta-advice surviving into saved documents; putting guidance in `SKILL.md` makes every invocation pay the token cost of all three guidance docs even if only one is being authored; dropping `references/` and relying on the template alone regresses output quality (vague NFRs, paraphrased FRs, weak alternatives). The three-way split is the smallest separation that preserves all three: clean produced documents, lean per-task context, and quality coaching. | Easy |
| MD-14 | All four kinds of supporting file (`SKILL.md`, `templates/`, `references/`, `question-sets/`) live **inside** the `staged-engineering-doc/` skill directory — bundled, not split with templates at the methodology root. | The skill must remain self-contained when installed. A user who copies or symlinks `staged-engineering-doc/` into `.claude/skills/` (project) or `~/.claude/skills/` (user scope) gets a working skill — templates included. An earlier layout had `templates/` at the methodology root and the skill referenced them by relative path; that broke the moment the skill was installed because the templates didn't travel with it. Bundling solves the install-time fragility. There is still only one canonical copy of each template — no copies, no drift. | Easy |
| MD-15 | The Plan's §6 Definition of Done is replicated as discrete `T-N.D*` tasks at the close of every branch's §7.x.9 task checklist (one task per DoD item, each with a runnable verification command). The DoD is never collapsed to a single "ensure §6 is satisfied" line. | Real-world testing surfaced that coding agents routinely forget the DoD when executing per-branch task lists. Causes: (1) §6 sits far from §7.x.9, so the DoD falls out of working context; (2) a single closing reference is easy to skim; (3) `[P]` subagents never see §6 unless the parent passes it; (4) Markdown checkboxes read as advisory unless gated. Replicating the DoD as concrete branch-local tasks turns it from advice into gated work the agent treats like any other task. SKILL.md additionally instructs the skill to recommend lifting DoD items into CI / pre-commit / PR-template gates when possible — that's the long-term answer, but until then, `T-N.D*` is the structural fix. | Easy (templates can collapse the block if a team adopts strong CI gates that subsume it) |
| MD-16 | Implementation tasks within a branch are grouped into atomic commits via explicit `T-N.C*` (Commit) tasks between implementation-task clusters. Commit-message format comes from the §5 `Commits` row, which is restated verbatim from the project's AGENTS.md (or equivalent). | Real-world testing also surfaced that agents routinely batch every change in a branch into a single `git commit` at the end. Same root cause as the DoD problem: commit boundaries are an implicit obligation, not a task. Making commits explicit `T-N.C*` tasks turns batching into an active error rather than a passive default. The format is sourced from AGENTS.md so the methodology stays DRY — there's no parallel "commit conventions" question or section. If AGENTS.md is silent, the skill asks once and writes the answer back to AGENTS.md so the next Plan inherits it. Atomic commits enable `git bisect`, make review tractable, and preserve back-derivability (one logical change per commit ≈ one Spec ID set per commit). DoD-fix work (lint warnings discovered during verification) becomes its own follow-up commit, never silently folded. | Easy (squash-on-merge teams can collapse history at PR time; the per-commit hygiene still matters for the review window) |
| MD-17 | Every Spec scenario, every quantified NFR, and every TC is bound to a verification entry via a Requirements Traceability Matrix (RTM) — specifically, a *Scenario Traceability Matrix* in Plan §12.1 plus the augmented §16 AC coverage matrix. Scenarios and quantified NFRs bind to runnable tests; TCs bind to a runnable test (mechanically verifiable TCs) **or** to a named reviewer / review-checklist citation (non-mechanical TCs). The binding mechanism is **tag-based, not table-based**: tests embed the Spec ID in canonical hyphenated form via a framework-native string or annotation (`@pytest.mark.scenario("S-04")`, `it("S-04: …")`, `t.Run("S-04", …)`, etc.); function-name bindings are acceptable but require a normalising regex in the gate. The matrix is derivable from `grep`. The Spec carries the obligation as meta-ACs `AC-50`/`AC-51`/`AC-52` in §11.5 *Test obligations*. DoD `T-N.D8` (scenarios → tests), `T-N.D9` (NFRs → measurement tests), and `T-N.D10` (TCs → §12 verification entry) are mechanical checks (`comm -23` between Spec-side IDs and the corresponding test-side or §12-side IDs). | Real-world runs of the methodology surfaced that coding agents ship features which pass unit tests but miss enumerated scenarios. Root cause: the Spec enumerates behaviour, but no structural mechanism binds each enumerated scenario to a runnable test. The Plan's test plan was a free-form per-category list (unit / integration / e2e) — categorising tests, not traceably covering the spec.<br><br>**Why RTM-style with tag binding, not Gherkin?** A 2025–2026 survey of AI-spec-driven frameworks (GitHub Spec Kit, AWS Kiro, OpenSpec, BMAD, PromptX) showed that none of them prescribes a scenario→test mapping with mechanical verification — they all link tasks to requirements but skip the test edge. The IEEE/ISO/IEC/IEEE 29148 RTM is the industry-standard term, already adopted in recent multi-agent AI papers (arXiv 2510.19868 loads RTMs into agent context). Tag-based binding is borrowed from BDD (Cucumber `@tag`) and the `swingerman/atdd` Claude Code plugin / Duvall's ATDD-driven AI development pattern; it survives refactors that a static table doesn't.<br><br>**Why not Gherkin/Cucumber wholesale?** Adopting Gherkin would give us binding for free but adds a step-definition maintenance tax, and there's a well-documented LLM failure mode ("summarises multi-step scenarios rather than executing them") — see arXiv 2504.07244 (already cited in §7.2) and the 2025 SCITEPRESS BDD-on-LLM paper. We get ~90% of the value with Given/When/Then prose + tagged tests, without the tooling burden. Teams already using BDD tooling can convert trivially. | Easy (teams that don't want the meta-ACs can remove §11.5 entries; gates relax accordingly) |
| MD-18 | Plan §14 *Risks & rollback* is restructured from free-form prose to an enumerated `R-NN` family (id / likelihood / severity / detection signal / mitigation task / rollback procedure). Each `R-*` must reference a mitigation path — either a task `T-N.*` in the branch checklists, an explicit `accepted (rationale: …)`, or `monitored only — see OBS-NN` (mechanically gated by `T-N.D17`). | Risks were previously prose at the bottom of the Plan; agents and reviewers consistently skipped them because nothing tied them to runnable work. Promoting risks to ID'd entities lets them be cited from `IMP-*` (§12.2) and bound to concrete mitigation tasks, the same structural move that worked for `D-*` decisions (`MD-05`) and the test-obligation gates (`MD-17`). Risk detection signals naturally point at an `OBS-*` row in §11 (`MD-19`), so the three sections (Observability, Risks, Impact) become a coherent operational layer instead of three disconnected lists. | Easy (teams uninterested in risk gating can leave the column empty; only `T-N.D17` regresses) |
| MD-19 | Plan §11 *Observability* is restructured from free-form prose to an enumerated `OBS-NN` family (id / signal / type / source / binds-to NFR or scenario / threshold / use). The Spec carries the obligation as new meta-AC `AC-54` in §11.5: every quantified `NFR-*` in §8 has at least one `OBS-*` row in Plan §11. Gated mechanically by Plan `T-N.D16`. | The methodology already quantifies NFRs (`MD-05` plus the quantified-NFR table in Spec §8), but the post-deploy *measurement* signal that proves the NFR was met in production was left implicit — a free-form table at the bottom of the Plan that agents routinely skipped. Quantification without a bound observability signal is half a contract: the Spec says `p95 < 200 ms` but no one wires the metric. Promoting observability to `OBS-*` rows with explicit NFR/scenario bindings closes the loop. Pairs with `MD-18` (risks reference `OBS-*` as detection signal) and `MD-20` (impact rows reference `OBS-*` for the consequence's monitoring channel). | Easy (teams that don't quantify NFRs effectively have no `AC-54` work; gate is a no-op) |
| MD-20 | New top-level family `IMP-NN` *Impact Records* in Plan §12.2 *Impact Traceability*. One row per identified consequence of the change, with a closed-vocabulary `scope` field (`code` / `system` / `business` / `external`), the triggering Spec ID(s), the linked risk (`R-*` if any), the linked observability signal (`OBS-*` if any), and the mitigation task (`T-N.*`). The Spec carries the obligation as new meta-AC `AC-53` in §11.5, recorded at **feature granularity**: the change has at least one `IMP-*` row for every materially-affected scope (`code` / `system` / `business` / `external`) — not one row per scenario. A single `IMP-*` row may cover several scenarios. Gated mechanically by Plan `T-N.D15` (§12.2 non-empty and every applicable scope represented). | Real-world runs of the methodology surfaced that coding agents reliably implement what the Spec says but under-reason about consequences — the "what did I just break?" question. Unit tests pass and the feature ships, but downstream consumers, business metrics, and external integrations are surprised. The existing §12.1 *Scenario Traceability Matrix* (`MD-17`) closes the *behavioural* gap (every scenario has a test). §12.2 closes the *consequence* gap (the change's consequences are enumerated and scoped to where they land). Impact is recorded per-feature rather than per-scenario deliberately: an early per-scenario draft of `AC-53` produced 20 mandatory rows for a 20-scenario feature — ceremony that buys little, since most scenarios share a handful of impacts. The single-family + `scope`-field design was chosen deliberately over four parallel prefixes (`IMPC` / `IMPS` / `IMPB` / `IMPE`): four prefixes would mean four DoD gates and four ID spaces to track, while a closed-vocabulary `scope` column gives the same filterability with one ID space and one gate. Teams that need stricter separation can still `grep -F "scope=external"` over §12.2. | Easy (teams that don't want impact gating can drop §12.2 + `AC-53` + `T-N.D15`) |
| MD-21 | The skill runs a two-pass *consistency check* before saving any document, as a mandatory part of `SKILL.md` Step 5. The recipes live in `skills/staged-engineering-doc/references/review-passes.md` (not inline in `SKILL.md`, per `MD-13`). **Self-consistency** (within-doc): every *referenced* ID resolves to a *defined* ID in the same doc, OPEN-Qs in the body match the handoff, prescribed sections are present. **Cross-consistency** (between-docs): every Spec `FR-*`/`NFR-*`/`TC-*`/`AC-*`/`S-*` cited by the Plan exists in the Spec, every Concept `D-*` cited by the Spec/Plan exists in the Concept, every OPEN-Q targeting a downstream stage is resolved or carried forward. Distinct from `MD-21` (`T-N.D18`/`D19`), which checks *a user's feature docs* for internal/cross-doc reference integrity — `MD-32` checks *the methodology's own source* for cross-skill closed-set consistency; different subject, maintainer-time lifecycle.<br><br>**Rejected alternatives.** (1) *A review-checklist item instead of a script.* Rejected — the pattern recurred three rounds *with* attentive review; a checklist is exactly what failed. (2) *Auto-discover the enumeration sites instead of a registry.* Rejected — "which sites are load-bearing" is a judgement, and a wrong auto-discovery would false-positive or false-negative silently; the explicit registry plus the automatic currency backstop is the honest split. (3) *A count-of-distinct-members check for every enumeration.* Rejected — an illustrative subset (`AC-50`/`AC-51`/`AC-52` as the test-obligation trio) is legitimate and would false-positive; the currency check keys on the *penultimate-implies-ultimate* signature, which fires only on the actual half-propagation shape, and the count check keys on the colon form that introduces a full list. (4) *Fold it into `spec-conformance` as a phase.* Rejected — `spec-conformance` audits a *user's feature* against its Spec; this audits the *methodology's own source* for cross-skill consistency. Different subject, different lifecycle. (5) *Wire it into `MD-21`'s two-pass check.* Rejected for the same reason — those passes run over a user's Concept/Spec/Plan, not over the plugin. | Easy (delete the script and this row; the closed sets still function — they just lose the mechanical drift-catch, and the discipline reverts to review, which is where it was through MD-01..MD-31). |
